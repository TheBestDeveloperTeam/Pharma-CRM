# Architecture Decision Record

## DR-001: Authentication Mechanism (Bearer JWT vs Session)

**Status:** Accepted

### Context
The Pharma CRM system requires secure authentication for four distinct user surfaces:
1. Super Admin Panel
2. Franchise Admin Panel
3. Mobile Sales App
4. Distributor Partner Portal

The backend is built in stateless PHP, designed to be deployed on shared cPanel hosting environments for smaller franchises, as well as scalable cloud environments for enterprise clients. We need to choose between traditional cookie-based PHP sessions and token-based authentication (JWT).

### Decision
We will use **Bearer-only JWT authentication coupled with opaque, rotating refresh tokens**.
- No cookies will be used for authentication.
- No native PHP sessions (`$_SESSION`) will be utilized.
- Tokens will be passed exclusively via the `Authorization: Bearer <token>` header.

### Rationale
1. **Stateless Scalability & Shared Hosting:** Native PHP sessions rely on disk-based file locks (by default on cPanel). This creates bottlenecks and makes load-balancing difficult without relying on external stores (like Redis), which are not always available on cheap shared hosting. JWTs are mathematically verified in-memory, requiring zero disk I/O.
2. **Zero CSRF Surface:** Because cookies are not used, Cross-Site Request Forgery (CSRF) attacks are structurally impossible. The browser will not automatically attach credentials to cross-origin requests. This drastically simplifies security middleware.
3. **Multi-Surface Clients:** The Mobile Sales App (built in Flutter/React Native) natively prefers header-based token auth. Using the exact same authentication paradigm across web portals and mobile apps unifies the backend architecture.
4. **Refresh Rotation & Security:** To mitigate the lack of server-side invalidation for JWTs, the access tokens are extremely short-lived (e.g., 15 minutes). The refresh token is an opaque database string. Upon use, the refresh token is rotated (a new one issued, old one invalidated). If an attacker steals and uses a refresh token, the legitimate user's client will eventually attempt to use the older token, triggering a reuse detection tripwire that revokes all tokens for that family, securing the account.

### Consequences
- **Strict CSP Requirement:** Storing tokens in `localStorage` or memory makes the application highly vulnerable to Cross-Site Scripting (XSS). We MUST enforce strict Content Security Policies (CSP) to prevent inline scripts and unauthorized external scripts.
- **XSS Mitigation:** XSS becomes the absolute primary threat vector. All output must be rigorously sanitized.
- **Session Lifecycle:** Browsers closing tabs will naturally clear `sessionStorage` (if stored there). This is intended behavior for shared computers, acting as an auto-logout.
- **Logout Propagation:** Logging out revokes the refresh token in the database, but the 15-minute access token remains technically valid until expiry.

### Trade-offs
We accept the trade-off of the short window of access token validity post-logout in exchange for completely stateless, lock-free verification on every API request. We accept the increased burden of XSS prevention to gain total immunity from CSRF and native mobile compatibility.
